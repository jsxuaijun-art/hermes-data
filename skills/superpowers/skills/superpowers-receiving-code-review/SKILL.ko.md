# 코드 리뷰 수용

## 개요

코드 리뷰는 감정적 동의가 아니라 기술적 평가입니다.

핵심 원칙: 구현 전에 검증합니다. 추측하기 전에 묻습니다. 사회적 편안함보다 기술적 정확성이 우선입니다.

## 응답 패턴

```text
리뷰 피드백을 받으면:

1. READ: 전체 피드백을 끝까지 읽습니다.
2. UNDERSTAND: 요구사항을 자기 말로 재정리하거나 질문합니다.
3. VERIFY: 코드베이스 현실과 대조합니다.
4. EVALUATE: 이 코드베이스에 기술적으로 맞는지 판단합니다.
5. RESPOND: 기술적 동의 또는 근거 있는 반론을 제시합니다.
6. IMPLEMENT: 한 항목씩 구현하고 각각 테스트합니다.
```

## 금지되는 반응

다음 반응은 피합니다.

- "맞습니다"라고 말하고 확인 없이 구현
- 리뷰어 권위를 이유로 기존 설계를 무시
- 여러 피드백을 한 번에 섞어 수정
- 테스트 없이 "수정했습니다"라고 말함
- 리뷰가 모호한데 임의 해석으로 진행
- 리뷰가 틀렸다고 느끼지만 근거 없이 방어

## 절차

### 1. 피드백 분류

각 피드백을 다음 중 하나로 분류합니다.

- 명확한 bug
- 요구사항 불일치
- 설계 개선
- style 또는 readability
- 질문 또는 제안
- 사실 확인이 필요한 주장

### 2. 검증

각 항목마다 코드, test, 문서, runtime behavior를 확인합니다. 리뷰어의 말이 맞는지, 이미 해결됐는지, 다른 곳에 영향이 있는지 확인합니다.

### 3. 결정

각 피드백에 대해 하나를 선택합니다.

- 수용: 기술적으로 맞고 변경이 필요합니다.
- 부분 수용: 핵심은 맞지만 구현 방식은 조정합니다.
- 보류: 정보가 부족해 질문이 필요합니다.
- 반려: 코드베이스 맥락상 틀렸고 근거를 제시합니다.

### 4. 구현

수용한 항목은 하나씩 수정합니다. 각 수정 후 관련 테스트를 실행합니다. 복수 항목이 독립적이면 작은 commit 또는 명확한 변경 묶음으로 유지합니다.

## 응답 형식

```text
검토 결과:
- [수용] <항목>: <근거와 수정 계획>
- [질문] <항목>: <필요한 확인>
- [반려] <항목>: <코드 근거>

실행한 검증:
- <명령>: <결과>
```

## 완료 전 확인

모든 변경 후 `superpowers-verification-before-completion`을 사용해 완료 주장을 하기 전에 최신 검증 결과를 확보합니다.
