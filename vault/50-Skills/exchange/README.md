## 二、三层交换机制

### L1 · 源码即文档（日常，最常用）

**不需要写工作文档。** 谁发现错、谁有新案由，**直接改源码**，改完在 `SKILL.md` 版本记录加一行。对方下次加载就能看到。

> 这是 80% 的情况。不要为了"交流"而写文档——改源码就是最好的交流。

**一句话原则：学习的载体是源码，不是文档。**
写出来能让对方"下次自动做对"的（某个数字、某条法条、某个案由、某条底线规则）→ **改源码**。
只有无法编码的东西（怎么挖出命门、为什么反直觉的取值才是好事）→ 才写文档。

**判据**：写之前问一句「这个能被规则化吗？」——能被规则化却写了三千字报告而源码一行没改，**那是聊天，不是协作**。

### L2 · 待核验清单（异步，成本最低）

**文件：`PENDING-待核验.md`**

Hermes 办案时遇到**不确定的文号、数字、法规版本**，不猜、不查、不硬给——直接丢进这个文件。
WorkBuddy 定期（或用户触发时）批量联网核验，把结果写回同一行，并在源码里改掉。

> 这是最高效的一层：**把不确定性集中管理**，避免每次一对一问答。

### L3 · 工作文档交换（定期 / 结案后，成本最高，价值最大）

两种文档，各用各的模板：

| 文档 | 谁写 | 模板 | 何时写 |
|---|---|---|---|
| **方法论增量** | Hermes | `_模板-方法论增量.md` | 新写一个案由 / 办完一个案子 / 发现更好的论证路径 |
| **时效核验报告** | WorkBuddy | `_模板-时效核验报告.md` | 核验完 PENDING / 定期全面核验 / 发现硬伤 |

写完放进 `归档/`，命名 `{日期}_{方}_{主题}.md`。

## 五、验收题机制（关键，别省）

**每份工作文档末尾必须附 1–3 个"验收题"——对方读完要能答出来的具体问题。**

为什么：长文档对方可能没真读进去。验收题是唯一的低成本确认方式。

**好验收题的标准**：一个问题，答案是一个具体数字/文号/一句话。

- ✅「2026-01-01 前的增值税核定引什么、之后引什么？」
- ✅「虚开专票罪的定罪门槛是多少？」
- ❌「你理解我的意思了吗？」

## 六、铁律（两边都要守）

1. **不留情面。** 发现问题直接指出，不要客套。上一轮 WorkBuddy 指出 Hermes 刑事数字过时，Hermes 指出后直接接受——这就对了。
2. **谁发现谁直接改源码**，不等对方确认。改完在 `SKILL.md` 版本记录加一行。
3. **书籍只提供方法与思路，不提供数字、不提供法条版本。** 凡数字与法条，一律视为高风险项。
4. **"废止"不等于"过往年度不能引"。** 引用前先确认涉案所属期——见 `SKILL.md` 时效分界规则。
5. **对外文书是工作底稿级**，提交前必须经持证人员复核。这条不因协作而放松。
6. **凭证不入版本库。** IP、Secret、Token、CorpID 一律不写进 vault（vault 会 git push）。

## 八、交叉验证要不要定时？（2026-09-13 定论）

**不单独定时。挂靠在月度核验的输出上。**

理由：交叉验证是**质量关卡**，应该跟着「有东西变了」走，不跟着日历走。日历式强制交叉会导致无变更时空转，很快变成形式主义。

三层安排：

| 层 | 是否定时 | 触发条件 |
|---|---|---|
| L1 源码层 | 否（事件驱动） | 谁改了源码，对方下次加载即看到 |
| L2 PENDING 层 | 否（随时丢） | Hermes 办案遇到不确定就丢 |
| **L3 交叉验证** | **跟月度核验走** | 核验报告的验收题 → 用户转 Hermes → Hermes 回传答案 |

**唯一的例外兜底**：月度核验时会检查 `CHANGELOG.md` 中状态为 🟡 且超过 30 天未被确认的条目，单独列出并提醒用户催确认。**防止有人改了但对方一直没看。**

## 九、交叉验证三问（每次改完都过一遍）

1. **数字对不对？**（税率、倍数、刑事门槛、期限、扣除标准）
2. **法条现行吗？**（是否废止、被替代、版本对不对）
3. **所属期与法条版本匹配吗？**

前两问主要由 WorkBuddy 核，第三问谁写案由谁先自查。
