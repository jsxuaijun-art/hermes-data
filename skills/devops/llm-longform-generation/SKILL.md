# LLM 长文出稿（流式直连）

## When to Use

任何**长文生成**任务（文案、口播稿、公众号文章、报告、方案）走第三方 OpenAI 兼容网关时使用本 skill。
典型触发：委派子代理写长稿结果整体超时无产出；或要一份超过几百字的成稿、怕调用中途断掉。

**不适用**：短问答、单轮工具调用、本地模型（llama.cpp/vLLM 自托管）——那些没有网关侧响应时长上限的问题。

## 核心规则

1. **长文一律走流式（`stream=true`）。** 非流式调用要求网关在响应时长上限内一次性返回全部内容；
   长稿生成耗时超过该上限就会被切断。流式则首字节很快回传、连接被持续保活，几千字也不受影响。
2. **拆小是次优解。** 把一份大任务拆成多次调用（如 A 稿一次、B 稿一次）能降低单次时长，
   但仍是碰运气；**流式才是根治**。两者可叠加使用。
3. **主会话只做编排/采集/验证**，成稿交给专门擅长的模型写（本机约定见下方"在用渠道"）。
   不要因为委派失败就自己在主会话里代写——那会破坏既定的模型分工纪律。
4. **密钥只从密钥文件/环境读**，绝不写进脚本正文、记忆或提交物（会随同步推到 GitHub）。

## 通用调用器

`scripts/stream_chat.py` — provider 无关的流式调用器，读 brief 文件、写 out 文件：

```bash
python3 scripts/stream_chat.py \
  --base-url https://aigw.telecomjs.com/v1 \
  --model Doubao-Seed-2.1-Pro \
  --key-env TELECOM_DOUBAO_KEY \
  --brief /tmp/brief.txt --out /tmp/draft.txt \
  [--system /tmp/system.txt] [--temperature 0.8] [--timeout 300]
```

- `--key-env` 给**环境变量名**，脚本自己从环境或 `~/.hermes/.env` 取真值 → 调用方不会碰到密钥明文。
- 逐行解析 SSE `data:` 帧，边收边打印，长任务可实时看到进度；`[DONE]` 结束。
- 适合直接改造成一次性任务脚本（把 brief 内联、out 指向桌面交付路径）。

## 在用渠道（本机，2026-10 实测）

| 用途 | 渠道 / 模型 | base_url | key 环境变量 |
|---|---|---|---|
| 短文案 / 短视频口播 | Doubao-Seed-2.1-Pro | `https://aigw.telecomjs.com/v1` | `TELECOM_DOUBAO_KEY` |
| 长文 / 文章 | kimi-k3 | `https://aigw.telecomjs.com/v1` | `TELECOM_KIMI_KEY` |

两条都实测支持流式；密钥在 `~/.hermes/.env`。渠道与 fallback 链的配置细节见
`hermes-free-model-channels`（user-owned）。

### 中途调 kimi 读图（含图任务，2026-10 实测）⚠️

主会话常用模型（deepseek-v4-flash）**没有视觉能力**，读不了客户发的图
（营业执照/财务报表/股权转让协议/截图等）。但不需要切换整个会话模型——
**在 deepseek 主会话里后台直接调 kimi-k3 的 API 即可**（与公众号 skill 调 kimi
同一条渠道 `aigw.telecomjs.com/v1`，密钥 `TELECOM_KIMI_KEY`）。

- **kimi-k3 实测支持图**：OpenAI 兼容 `image_url` 格式（`data:image/png;base64,...`），
  能准确识别图中文字/内容。**key = 用 kimi 读图，而不是把主会话切到 kimi**。
- **通用调用脚本**：`scripts/kimi_chat.py` — 支持文字 + 多张图片混合输入，
  模型默认 kimi-k3：
  ```bash
  python3 scripts/kimi_chat.py --text "读取这些图，提取XX信息" \
      --images /a.png,/b.jpg --out /tmp/result.txt [--key-env TELECOM_KIMI_KEY]
  ```
- **响应读取**：读 `choices[0].message.content`（kimi 的推理见 `reasoning_content`，
  别把 reasoning 当正文）。
- **用前探测**：正式调用前先拿一张小图真实探测通道（脚本已内置可复用思路），
  防 503 无可用渠道/模型名失效。
- **分工**：读图/处理含图材料 → kimi；编排/采集/验证/汇报 → deepseek 主会话。

## 创作类委派：简报必须自带「已核实事实白名单」

把文案/方向的创作交给外部模型（豆包/kimi）时，**主会话必须先核实事实，再把事实作为白名单写进 brief**，
并把「不许编」写成硬约束条目。否则创作模型会自己补细节，产出看着很专业但带着幻觉，回来还得整篇返工。

brief 的固定骨架（实测有效，2026-10 短视频选题）：

```
【任务】不是写成稿 / 是出方向供拍板 —— 一句话说清交付形态
【已核实事实（只能用这些，不得自行添加法条/数字）】
  1. <法规名>（<文号>，<施行日期>）第X条：……
  2. …                                    ← 每条都可回溯到官方源
【平台与算法口径】观众1.7秒决定去留 / 权重 收藏>复访>5秒完播>评论 / 差评是乘法级扣分
【硬约束】
  - 不得编造具体客户案例、具体数字、具体地点（"有个客户说…""罚了XX万"这类一律不许编）；
    可以讲法条里真实存在的罚则区间。
  - 语气/受众/口径要求
【请输出】编号化结构（先给判断 → 候选方向（每个含钩子/前3秒原话/机制/落业务点/风险）→ 推荐排序）
```

两条要点：
- **事实条目标明文号+施行日期**，让创作模型引不错；核实时若发现网上流传的文号是错的（如人资许可
  常被传成"人社部令第47号"，实为**第50号**），要在 brief 里显式纠偏一句。
- 要它同时输出**风险/不适用情形**，主会话才能据此做取舍——创作模型只负责想，把关留在主会话。

## 稿件回收后的自检（主会话职责，2026-10 实测）

创作模型交回来的稿子**不能直接转发**。三条必查项，都是踩过的：

1. **模型自报的时长/字数是零信任项，自己在主会话里重算。**
   本次豆包把 234 / 237 字的短视频口播稿标成"约60秒"（实际 36 秒），六条稿里有两条错标。
   口播时长按**汉字数**算：`秒 ≈ 汉字数 / 6.5`（250 字 ≈ 38 秒）。
   凡稿子里出现"约X秒 / 约X分钟 / X字"，一律复算后改，并让**速览表与正文口径一致**：

   ```python
   import re
   n = len(re.findall(r"[\u4e00-\u9fff]", draft))   # 只数汉字，不含标点/数字/英文
   seconds = max(30, round(n / 6.5))
   ```

2. **占位符会被塞到语法不通的位置。** 主会话要求"主体未定处用【待确认：XX】占位"时，
   创作模型常把它当**主语/定语**插进句子中间，例如
   "【待确认：证书主体】只要没有较严重不良信用记录…"——而那句讲的是**申请人条件**、与证件无关，
   读起来立刻别扭。对策：交付前**通读一遍**，该句本不涉及该事实就**删掉错位占位符**，
   涉及就移到它真正该在的位置。**删错位占位 ≠ 代写，这是可机械修正的缺陷。**

3. **法规文号常被漏掉。** 模型写"按照2018年7月施行的《人力资源市场暂行条例》要求"，省掉了文号 →
   补成"《人力资源市场暂行条例》（国务院令第700号，2018年7月1日施行）第三十六条"。
   凡法规名首次出现**必须带文号**，且以 brief 白名单里的为准（文号错 = 硬伤，如人资许可常被写成"第47号"，实为**第50号**）。

**边界（别越线）**：主会话的自检只做**机械修正**——删错位占位符、补文号、改与白名单冲突的数字/表述、
校准时长。**不得改文风、不得重写句意、不得增删观点**：那是代写，会破坏模型分工纪律。

改动要在交付消息里**逐条说明改了哪几处、为什么**（本次三条：时长由"约60秒"改 36 秒、两处错位占位符、
一处补文号），让用户能逐条核。**"我没改文案，只修了三处事实/格式缺陷"——这个交代本身就是交付质量的一部分。**

推理型模型（先思考后作答）走 SSE 时，**先长时间吐 `reasoning_content`，`content` 可能几分钟后才开始**。
只解析 `content` 的脚本会出现：

- 进程活着、CPU 在跑，但 **out/log 文件长时间为 0 字节**（3-6 分钟都正常）；
- `--timeout` / read timeout 要按**总时长**给足（实测一次 6k token 的方向分析约 5-6 分钟，日志 0 字节持续 3.7 分钟）。

**处置铁律：不要因为"没输出"就判卡死、杀进程、改判模型不可用。** 正确做法：`background=true` 起任务 +
`notify=true`，然后 `process(action="poll")` 看 `status/uptime_seconds`（running 就别动）；
真要看进度用 `wc -c <log>`——**0 字节不等于失败**。想实时看到思考过程，把 `delta.reasoning_content` 也打印出来
（但落盘的正式产物只存 `content`）。

## Pitfalls

- **别把"非流式超时"当成"模型不可用"**：换模型通常没用，换调用方式（流式）才对症。判断方法——
  短问答能通、长稿才断，就是响应时长问题，不是链路问题。
- **别把"推理阶段无输出"当卡死**：见上节。日志 0 字节 + 进程 running = 还在思考，耐心等或后台挂着，
  杀掉只会白烧一次调用。判据是进程状态与 uptime，不是日志大小。
- **委派失败要如实说明并换路子**，不要在对话里含糊过去；也不要把失败的那次当作"产出已交"。
- **SSE 解析要容错**：帧可能带空行、`data: [DONE]`、或非法 JSON 心跳，解析异常要 `continue` 而不是崩掉。
- **超时要给足**：`timeout` 是"读超时"，流式下应设 300s 量级，别用默认值。
- 长稿输出**落地成文件**再引用（`out` 路径），不要只依赖终端回显——便于核对字数与后续排版。
- **别转发模型自报的时长/数字**：时长按汉字数 `/6.5` 复算，文号按白名单核对，占位符通读查错位——模型自述的数字一律零信任（本次两条稿的"约60秒"都是错的）。
- **自检 ≠ 代写**：只做机械修正（删错位占位符、补文号、对齐白名单、校准时长），**文风与句意不动**；改了什么必须在交付消息里逐条说明，别默默改。

## Verification

1. 脚本退出码 0，且打印 `已保存: <path> (N 字)`，N 与预期量级相符（不是空文件、不是几十字）。
2. `read_file` 打开产物确认是完整成稿（有结尾，不是被截断在半句）。
3. 若产物要交付，再走一遍排版/落盘（如转 .docx）并核对交付路径存在。
4. **回收稿已过三道自检**：时长/字数按汉字数复算并改对；占位符位置通读无误；法规首次出现均带文号。
5. **改动清单已逐条写进交付消息**（改了几处、哪几处、为什么），用户可逐条核。
