# 아이디어를 설계로 구체화하기

거친 아이디어를 자연스러운 협업 대화로 명확한 설계와 명세로 바꿉니다.

먼저 현재 프로젝트 맥락을 파악한 뒤, 한 번에 하나씩 질문해 목적과 제약을 정제합니다. 무엇을 만들지 충분히 이해하면 설계를 제시하고 사용자 승인을 받습니다.

<HARD-GATE>
설계를 제시하고 사용자가 승인하기 전에는 구현 스킬을 호출하거나, 코드를 작성하거나, 프로젝트를 scaffold하거나, 어떤 구현 행동도 하지 마십시오. 간단해 보이는 작업에도 동일하게 적용됩니다.
</HARD-GATE>

## 안티패턴: "너무 단순해서 설계가 필요 없다"

모든 프로젝트는 이 과정을 거칩니다. todo list, 단일 함수 utility, config 변경도 예외가 아닙니다. 단순한 작업일수록 검증되지 않은 가정으로 낭비가 생깁니다. 설계는 짧아도 되지만 반드시 제시하고 승인을 받아야 합니다.

## 체크리스트

각 항목을 task로 만들고 순서대로 완료합니다.

1. **프로젝트 맥락 탐색** - 파일, 문서, 최근 commit을 확인합니다.
2. **시각적 companion 제안** - 시각적 판단이 필요한 주제라면 별도 메시지로 제안합니다.
3. **명확화 질문** - 목적, 제약, 성공 기준을 한 번에 하나씩 묻습니다.
4. **2-3개 접근안 제시** - trade-off와 추천안을 설명합니다.
5. **설계 제시** - 복잡도에 맞게 section으로 나누어 검토를 받습니다.
6. **승인 받기** - 사용자가 명시적으로 승인할 때까지 구현으로 넘어가지 않습니다.
7. **설계 저장** - 적절한 위치에 spec 문서를 남깁니다.
8. **구현 전환** - 승인 후 `superpowers-writing-plans`를 호출합니다.

## 절차

### 1. 맥락 탐색

구현하지 않고 읽기만 합니다. README, package/config, 기존 architecture, test, 최근 변경을 확인해 현재 시스템이 어떤 문제를 풀고 있는지 파악합니다.

### 2. 시각적 companion 제안

UI, diagram, flow, layout처럼 시각적 논의가 도움이 되면 다음 메시지만 단독으로 보냅니다.

```text
이 주제는 시각적 선택지가 있을 수 있습니다. 원하면 browser 기반 visual companion으로 mockup, diagram, option을 함께 보면서 정리할 수 있습니다.
```

사용자 답변을 기다립니다. 거절하면 text-only로 진행합니다. 자세한 내용은 `visual-companion.md`를 참고합니다.

### 3. 질문

한 번에 하나의 질문만 합니다. 사용자의 답을 반영해 다음 질문을 고릅니다. 목표는 다음을 명확히 하는 것입니다.

- 실제 사용자가 누구인지
- 작업의 성공 기준
- 반드시 지켜야 할 제약
- 제외할 범위
- 기존 시스템과의 연결 지점

### 4. 접근안

충분히 이해했으면 2-3개 선택지를 제시합니다. 각 선택지는 장점, 단점, 위험, 추천 여부를 포함합니다. 추천안을 분명히 말하되 사용자가 선택하게 둡니다.

### 5. 설계 제시와 승인

설계를 읽기 쉬운 단위로 제시합니다. 큰 설계는 section별로 승인받고, 작은 설계는 한 번에 제시할 수 있습니다.

승인 전에는 구현하지 않습니다. 사용자가 수정 요청을 하면 설계를 고친 뒤 다시 승인받습니다.

### 6. 저장과 다음 단계

승인된 설계를 `docs/superpowers/specs/YYYY-MM-DD-<feature>.md`에 저장합니다. 사용자의 위치 선호가 있으면 그것을 따릅니다.

그 다음 `superpowers-writing-plans`를 호출해 구현 계획을 만듭니다. brainstorming 직후 바로 구현 스킬로 넘어가지 않습니다.

## 결과물

완료 시 다음이 있어야 합니다.

- 사용자가 승인한 설계
- 저장된 spec 문서
- open question 또는 제외 범위 목록
- 다음 단계로 `superpowers-writing-plans` 호출
