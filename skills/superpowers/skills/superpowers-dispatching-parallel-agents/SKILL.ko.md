# 병렬 Agent Dispatch

## 개요

서로 독립적인 문제 영역마다 별도 agent를 보냅니다. 각 agent에는 필요한 맥락만 정확히 제공하고, 현재 session history 전체를 넘기지 않습니다. 이렇게 하면 agent가 자기 작업에 집중하고, 메인 session은 조정과 통합에 집중할 수 있습니다.

여러 test failure, 서로 다른 subsystem bug, 독립 조사 작업을 순차로 처리하면 시간이 낭비됩니다. 독립이면 병렬로 보냅니다.

핵심 원칙: 독립 문제 영역마다 agent 하나를 보냅니다.

## 사용 시점

다음 조건을 모두 만족할 때 사용합니다.

- 작업이 2개 이상입니다.
- 각 작업이 서로 다른 파일, subsystem, failure, 조사 범위를 다룹니다.
- 한 작업의 결과가 다른 작업의 시작 조건이 아닙니다.
- 충돌 가능한 write scope를 분리할 수 있습니다.

사용하지 말아야 할 때:

- 다음 action이 특정 답변 하나에 막혀 있습니다.
- 작업들이 같은 파일을 동시에 편집해야 합니다.
- 문제 정의가 아직 불분명합니다.
- subagent가 없는 환경입니다. 이 경우 직접 순차 처리합니다.

## Dispatch 전 확인

1. 독립성을 확인합니다.
2. 각 agent의 범위를 좁힙니다.
3. 필요한 파일, 명령, 기대 출력만 제공합니다.
4. write task라면 소유 파일을 명시합니다.
5. 다른 agent도 작업 중일 수 있으므로 기존 변경을 되돌리지 말라고 지시합니다.

## 좋은 지시문 구조

```text
Task: <명확한 목표>

Context:
- <필요한 배경만>
- <관련 파일>

Scope:
- Read: <읽을 수 있는 영역>
- Write: <수정 가능한 파일 또는 모듈>

Do:
- <구체 작업>
- <검증 명령>

Do not:
- unrelated refactor 금지
- 다른 agent 또는 사용자의 변경 revert 금지

Return:
- findings 또는 변경 파일 목록
- 실행한 검증과 결과
- 남은 위험
```

## 병렬 실행 후 통합

agent 결과가 오면 그대로 믿고 끝내지 않습니다. 다음을 확인합니다.

- 결과가 원래 질문에 답하는지
- 파일 변경 scope가 지켜졌는지
- 서로 충돌하거나 중복되는 결론이 있는지
- 검증 결과가 실제로 충분한지

필요하면 메인 session에서 통합 patch를 만들고 최종 검증을 실행합니다.

## 실패 처리

agent가 막히면 막힌 지점을 확인합니다. 정보 부족이면 추가 context를 보내고, scope가 잘못됐으면 중단 후 새 task로 분리합니다. 독립성이 깨졌다면 병렬 처리를 멈추고 메인 session에서 순서를 재정의합니다.
