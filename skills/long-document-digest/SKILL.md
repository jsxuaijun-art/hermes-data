# 大部头文档 → 精读 → 归档 → 融入 skill

把用户投喂的**大文档**（一本书、一份 PDF、法规汇编、长报告，几百页 / 数十万字）转成三样东西：
① 知识库（Obsidian）里可检索的结构化笔记；② 一份精华速查；③ 融入相关 skill 的 reference。
**不做**：顺序通读全文、把整本书原样搬进知识库、把书里的数字当现行规定引用。

这是本用户的**日常场景**（常年投喂 PDF 与材料），不是一次性任务。

## When to Use

- 用户给来一本书/长 PDF/法规汇编，要求"提取并分析""形成 md 存 Obsidian""总结后融入 skill"。
- 用户问"转成 md 会不会变小""之前上传的文件还能找到吗"。
- 需要把**外部权威材料**的结论沉淀成可复用的 skill 内容。

不适用：短材料（几页、一两千字）→ 直接读、直接融，不必走本流程。
不适用：用户要的是**摘要**而非本体知识库归档 → 走普通总结。

## Prerequisites

- PDF 文本抽取：`pymupdf`（首选，能按页/按章定位）、`pypdf`、`pdfplumber`。
- 通用文档转换：MarkItDown（命令名 `mdconv`），适合版式简单或格式杂的输入。
- 图片型/扫描件：需 OCR（tesseract），文字层为空时先判页是否有文字层。
- 知识库：确认 vault 路径（本库 `D:\obsidian-vault`），**先列目录看现有分类再决定落点**。

## How to Run

```
1. 确认来源与体量（页数、字数、抽取后体积）——顺带回答"转 md 是否变小"
2. 结构骨架化：编—章—节层级 + 精华栏目 + 索引/附表清单   ← 先做，别跳
3. 只精读"精华栏目"（结论型内容），其余只留索引
4. 归档：总览索引 + 每逻辑单元一份 + 精华速查一份（带 frontmatter）
5. 融入 skill：方法论入库，数字/文号标「待核」并列清单
6. 留痕：skill 版本记录加一行；文档里点明要补的条目这次就补上
```

## Quick Reference

| 问题 | 答案 |
|---|---|
| 转 md 会变小吗 | 图片型 PDF：会，约 1/8（8.86 MB → 1.10 MB 实测）。已是 md/txt：白干，体积没变化 |
| 早前上传的文件还能找回吗 | **不能。Hermes 没有上传文档库**（即读即用、不落档）。直接问用户路径，别去翻 `~/.hermes/` |
| 该精读多少 | 5%–10%。45.6 万字的书 → 只精读 4.2 万字的"结论型栏目"即可覆盖全书核心 |
| 书里的数字能直接用吗 | **不能**。书只提供方法与思路，不提供数字。一律标「待核」 |
| 能不能派子代理分担阅读 | **不能按大块派**（见 Pitfalls 第一条） |
| 归档切几份 | 1 份总览索引 + 每逻辑单元 1 份 + 1 份精华速查 |

## Procedure

### 第 1 步：确认来源与体量（同时回答用户的体积问题）

抽取全文，记录三个数字：**原文件体积 / 抽取后纯文字体积 / 页数与字数**。
这是用户必问的"转 md 会不会变小"的唯一诚实答法——给实测比例，不要泛泛说"会变小"。

顺带纠正一个常见误解：**Hermes 没有"上传文档库"**。用户上传的文件即读即用、不落档，
没有 uploads / documents / 缓存目录保存历史附件。用户问"之前上传的还能找回来吗"，
**直接说明没有存档并索取路径**——原文件始终在用户自己的位置（OneDrive 桌面、微信下载目录等）。

### 第 2 步：结构骨架化（**先做这一步，再读正文**）

**不要一上来顺序通读。**先程序化抽骨架，拿到"地图"：

- 抽出**编—章—节**层级与页号；
- 识别书里的**"精华型"固定栏目**（结论型内容：疑难解答 / 要点 / 案例评析 / 实务精解），列出全部条目；
- 抽出全部**索引与清单型内容**（案例表、法条表、附表）。

收益：一眼看出"哪里是骨、哪里是肉"，据此决定精读范围，而不是把几十万字均匀分配。

### 第 3 步：只精读精华栏目

大部头里真正可复用的通常只占 5%–10%，且高度集中在固定栏目。
**把结论型栏目整块抽出来单独精读**，收益比通读高一个数量级。
其余部分只保留骨架索引，不精读——将来要查再定点回原文。

### 第 4 步：归档到知识库

- **落点**：按 vault 现有分类走（本库 `D:\obsidian-vault\30-Knowledge\<主题>\`），
  先列目录看已有分类，**不要新建平行体系**。
- **切分**：1 份**总览索引**（结构 + 核心结论一句话表 + 案例索引 + 用法 + 时效存疑）
  + 每个逻辑单元（编/部分）1 份 + 1 份**精华速查**（把散落结论集中成一张表，将来最常被翻的就是它）。
- **每份都要**：YAML frontmatter（`title` / `tags` / **`来源`**（书名+作者+出版社+年份+ISBN）/ `收录` 日期），
  **来源字段是这份笔记的身份证，不能省**。
- 交叉链接用 `[[路径]]` 指向库内相关笔记；章节名里带数字/文号的，照原文抄，不要"顺手规范"。
- 交付报路径一律用 **Windows 盘符**（`D:\...`），不用 WSL 路径。

### 第 5 步：融入 skill（方法论进去，数字标待核）

**分两件事，不要混**：

| 可安全融入 | 必须打标 / 核验 |
|---|---|
| 方法论、论证顺序、判断框架、命门识别思路、案例胜负逻辑 | **一切数字**：税率、比例、门槛、期限、金额 |
| 结构性清单（案由表、文书清单） | **一切文号**：文件名、文号、条款序号 |

来源是**有出版年份的书**时尤其严格——书写完那天，数字就开始过期。
做法：在目标 skill 的 reference 文件里单列「**待核清单**」一节，逐条列出需联网核验的项，
并写清"以哪个新规为准"（例：刑法数额→法释〔2024〕4号；增值税→2026-01-01《增值税法》为界）。

> 作者立场有争议的，写"**作者持某意见**"，不要写成定论。

### 第 6 步：留痕与收尾

- 在目标 skill 的**版本变更记录加一行**：来源书/文件、新增了哪个 reference、发现的时效风险。
  没有这一行，下一个会话没人知道这份 reference 从哪来、能不能信。
- **文档里点明要补的条目，这次就补上**，不要留成 TODO——否则留给下一个会话的是一句没有上下文的话。

## Pitfalls

- **不要用"一个子代理读一大块"分担大文档阅读。** 已实测：把书切 4 块派 4 个 `delegate_task`
  并行精读 → 每块输入过大 → **集体撞 TPM 限流(429)被截断 → 四个子代理一个文件都没写成，整轮白费**
  （且失败发生在后台，你往往已经往前走了）。
  规则：要读的量本身很大（每块 >2 万字）→ **程序化抽取 + 自己精读关键块**。
  子代理适合"**输入小、思考重**"，不适合"**输入大、判读为主**"。
  确实要派时：**每块压到 1–2 万字以内，并要求先写文件再总结**，截断了产出也落在磁盘上。
- **不要一上来顺序通读大文档**——浪费，且抓不住重点。
- **不要把书里的数字/文号当现行规定写进交付物**——出版年份一到就过期，会直接导致对外文书引错法。
- **不要在 vault 里另起一套平行目录**——先看现有分类。
- **不要泛泛回答"转 md 会变小"**——给实测数字。
- **不要去找"上传文档存档"**——不存在，直接问路径。
- **不要只交"归档完成"就算完**——不在 skill 版本记录里留痕，等于没沉淀。

## Verification

交付前逐条核：

- [ ] 抽出体积/字数与页数已记录，并据实回答"转 md 是否变小"
- [ ] 骨架已抽全（编章节 + 精华栏目条目数 + 索引/附表数），条目数与原文对得上
- [ ] 知识库文件全部带 frontmatter，**`来源` 字段完整**（含出版社与年份）
- [ ] 总览文件里有「时效与存疑」一节
- [ ] 融入 skill 的 reference 里有「待核清单」，且每条写清以哪个新规为准
- [ ] 目标 skill 的版本变更记录加了新行
- [ ] 交付路径用 Windows 盘符
- [ ] 没有留下未说明的 TODO
